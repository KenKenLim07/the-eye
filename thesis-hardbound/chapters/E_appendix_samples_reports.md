# Appendix E — Sample Inputs, Outputs, and Reports

This appendix provides representative inputs/outputs produced by PH VibeCheck AI to support traceability of results in the main chapters.

## Sample input: manual benchmark CSV (real-news sample)

File:
- `backend/reports/benchmark_sample_2026-03-25_2026-03-31.csv`

Header fields (abridged):
- `article_id, source, published_at, url, title, content, tagalog_signal_ratio, label_a, label_b, label_final, ...`

Purpose:
- serves as the labeling worksheet (two annotators + adjudication)
- stores model outputs per row so evaluation scripts can compute metrics consistently

## Sample output: benchmark evaluation JSON report

File:
- `backend/reports/sentiment_benchmark_2026-03-25_2026-03-31.json`

Top-level sections (keys):
- `models` — per-model metrics and confusion matrices (VADER, DistilBERT, Hybrid)
- `hybrid_routes` — route counts and route-level summaries (VADER vs DistilBERT path usage)
- `kappa` / `kappa_n` — inter-annotator agreement summary
- `runtime_settings` — thresholds and evaluation toggles used for the run

This JSON is used as the “source of truth” for the reported benchmark tables and values in Chapter 5.

## Sample output: stored sentiment row with routing metadata (database)

Sentiment results are stored in the database as:
- an internal analysis row in `bias_analysis` (includes detailed `model_metadata`), and
- a public cache row in `article_sentiment_public` (includes the latest `sentiment_label` and `sentiment_score` per article).

Example fields recorded in `bias_analysis.model_metadata` for hybrid sentiment:
- `route` (e.g., `vader`, `distilbert`, `vader_fallback`)
- `route_reason` (e.g., `tagalog_signal`, `reporting_preface`)
- `tagalog_signal_ratio`, `tagalog_signal_threshold`
- per-engine metadata under `route_metadata` (e.g., truncation stats for transformer, PH patch status for VADER)

These metadata fields support auditability: a reviewer can inspect why a particular pathway and label were produced for a given article.

## Sample outputs for dashboards (derived aggregates)

The system produces aggregated outputs used by the dashboards, including:
- time-series sentiment trends (daily averages and counts per source)
- cross-source correlation inputs (aligned daily aggregates)
- entity rankings (frequency and average sentiment associated with entity mentions)

These aggregates are generated by backend endpoints and/or snapshot scripts, and are designed to support drill-down from summary views to the underlying article-level records for qualitative verification.

## Web application inputs and outputs (UI-facing)

For the running web application, “inputs” and “outputs” can be understood as:

**User inputs (examples):**
- selecting an observation window (e.g., last 7 days)
- toggling “include today”
- entering a keyword query in the Search view
- selecting a source/outlet filter

**System outputs (examples):**
- dashboard visualizations (Trends, Correlation, Entities) rendered from aggregated sentiment/entity signals
- article-level pages that allow qualitative verification of aggregated patterns

To document UI-facing outputs in the hardbound manuscript, the recommended evidence is:
1. **screenshots of the dashboards** (saved under `thesis-hardbound/figures/` and referenced in Chapter 5), and
2. **sample API request/response pairs** (e.g., `GET /ml/trends`, `GET /ml/correlation`, `GET /ml/entities`) shown as short JSON snippets when needed.
